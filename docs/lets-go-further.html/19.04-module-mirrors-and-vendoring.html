Chapter 19.4.

Module mirrors and vendoring

One of the risks of using third-party packages in your Go code is that the version control repository where it is hosted (e.g GitHub, GitLab or BitBucket) will be temporarily unavailable when you need to fetch a copy of the code. Or worse, the owner might delete the repository altogether without adequate warning. For example, the httprouter package plays a central part in our application, and if the author ever decided to delete it from GitHub it would cause us quite a headache to scramble and replace it with an alternative.

(I’m not suggesting this is likely to happen with httprouter — just using it as an example!)

Fortunately, Go provides two ways in which we can mitigate this risk: module mirrors and vendoring.

Module mirrors

Go supports using module mirrors (sometimes also known as module proxies), which are services that mirror source code from the original, authoritative, repositories.

The most well-known (and well-used) module mirror is proxy.golang.org, which is maintained by the Go team at Google and contains copies of the source code from tens of thousands of open-source Go repositories.

By default, whenever you fetch a module using go get or one of the go mod * commands, the go tool will first attempt to retrieve the appropriate version of the source code from the proxy.golang.org mirror. If it can’t be found in the mirror, then it will fall back to fetching the code from the authoritative repository.

If you run the go env command on your machine, you should see that there is a GOPROXY environment variable setting similar to this:

This setting contains the list of sources that the go tool will fetch source code from, separated by commas (,) or pipes (|).

Unless you’ve already changed it from the default value, you should see that the GOPROXY setting equals 'https://proxy.golang.org,direct'. This means that the go tool will try to fetch source code from https://proxy.golang.org first, then fall back to fetching a copy directly from the authoritative host (thanks to the direct directive).

You can change this to use alternative module mirrors — such as goproxy.io — if you prefer. It’s important to explain that if you use the pipe character | as a separator, rather than a comma, it subtly changes the behavior.

When a comma is used as the separator, the go tool will fall back to fetching from the next source only after receiving a 404 (not found) or 410 (gone) HTTP response from the mirror. If there is any other error, including a network timeout, the error is considered terminal and the fetch will fail.

Whereas if you use | as the separator, it will fall back to trying the next source after any error, which is useful if the mirror is temporarily unavailable or experiencing problems.

But in general, I recommend leaving GOPROXY with its default setting unless you have a good reason to change it — like you want to use an alternative mirror, or proxy.golang.org is unavailable for a long period of time.

Vendoring

Go’s module mirror functionality is great, but it isn’t a silver bullet for all developers and all projects.

For example, perhaps you don’t trust or wish to rely on module mirrors provided by Google or other third-parties. Or maybe you need to routinely work in an environment without network access. In those scenarios you probably still want to mitigate the risk of a disappearing dependency, but using a module mirror isn’t possible or appealing.

You should also be aware that the default proxy.golang.org module mirror doesn’t absolutely guarantee that it will store source code forever. From the FAQs:

proxy.golang.org does not save all modules forever. There are a number of reasons for this, but one reason is if proxy.golang.org is not able to detect a suitable license. In this case, only a temporarily cached copy of the module will be made available, and may become unavailable if it is removed from the original source and becomes outdated.

Additionally, if you need to come back to a ‘cold’ codebase in 5 or 10 years’ time, will the proxy.golang.org module mirror still be available? Hopefully it will — but it’s hard to say for sure.

So, for these reasons, it can still be sensible to vendor your project dependencies using the go mod vendor command. Vendoring dependencies in this way basically stores a complete copy of the source code for third-party packages in a vendor folder in your project.

  • The go mod tidy command will make sure the go.mod and go.sum files list all the necessary dependencies for our project (and no unnecessary ones).
  • The go mod verify command will verify that the dependencies stored in your module cache (located on your machine at $GOPATH/pkg/mod) match the checksums in the go.sum file.
  • The go mod vendor command will then copy the necessary source code from your module cache into a new vendor directory in your project root.

Because all the dependency source code is now stored in your project repository itself, it’s easy to check it into Git (or an alternative version control system) alongside the rest of your code. This is reassuring because it gives you ownership of all the code used to build and run your applications, kept under version control.

The downside of this, of course, is that it adds size and bloat to your project repository. This is of particular concern in projects that have a lot of dependencies and the repository will be cloned a lot, such as projects where a CI/CD system clones the repository with each new commit.

This vendor/modules.txt file is essentially a manifest of the vendored packages and their version numbers. When vendoring is being used, the go tool will check that the module version numbers in modules.txt are consistent with the version numbers in the go.mod file. If there’s any inconsistency, then the go tool will report an error.

Note: It’s important to point out that there’s no easy way to verify that the checksums of the vendored dependencies match the checksums in the go.sum file. Or, in other words, there’s no equivalent to go mod verify which works directly on the contents of the vendor folder.

To mitigate that, it’s a good idea to run both go mod verify and go mod vendor regularly — which is one of the reasons for including them both as part of the make tidy rule. Using go mod verify will verify that the dependencies in your module cache match the go.sum file, and go mod vendor will copy those same dependencies from the module cache into your vendor folder.

Lastly, you should avoid making any changes to the code in the vendor directory. Doing so can potentially cause confusion (because the code would no longer be consistent with the original version of the source code) and — besides — running go mod vendor will overwrite any changes you make each time you run it. If you need to change the code for a dependency, it’s much better to fork it and import the forked version instead.

Additional information

Inconsistent vendoring error

Every time you add, remove or upgrade a dependency, make sure to run go mod vendor or the make tidy command immediately afterwards to synchronize the contents of the vendor folder with your go.mod file. If you don’t, you’ll run into an “inconsistent vendoring” error similar to this:

The ./… pattern

Most of the go tools support the ./... wildcard pattern, like go fmt ./..., go vet ./... and go test ./.... This pattern matches the current directory and all sub-directories, excluding the vendor directory.

Generally speaking, this is useful because it means that we’re not formatting, vetting or testing the code in our vendor directory unnecessarily — and our make audit rule won’t fail due to any problems that might exist within those vendored packages.

Authenticating requests

Now that our clients have a way to exchange their credentials for an authentication token, let’s look at how we can use that token to authenticate them, so we know exactly which user a request is coming from.

Essentially, once a client has an authentication token we will expect them to include it with all subsequent requests in an Authorization header, like so:

When we receive these requests, we’ll use a new authenticate() middleware method to execute the following logic:

  • If no Authorization header was provided at all, then we will call the next handler in the chain as normal with no further action.
  • If the Authorization header is provided but the token is not valid, then we will send the client a 401 Unauthorized response and an error message to let them know that their token is malformed or invalid.
  • If the Authorization header is provided and the token is valid, then we know that the user has authenticated. We look up the user’s details from the database, store these details in the request context, and then call the next handler in the chain.

Reading and writing to the request context

The other setup step, before we get into creating the authenticate() middleware itself, relates to storing the authenticated user’s details in the request context.

We discussed what request context is and how to use it in detail in Let’s Go, so if any of this feels unfamiliar then I recommend rereading that section of the book before continuing. But as a quick reminder:

  • Every http.Request that our application processes has a context.Context embedded in it, which we can use to store key-value pairs containing arbitrary data during the lifetime of the request. In this case we want to store a User struct containing the authenticated user’s information.

  • Any values stored in the request context have the type any. This means that after retrieving a value from the request context you need to assert it back to its original type before using it.

  • It’s good practice to use your own custom type for the request context keys. This helps prevent naming collisions between your code and any third-party packages which are also using the request context to store information.
